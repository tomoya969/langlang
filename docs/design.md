## 入力欄のカーソル（2026-10-24）

途中の 1 字母だけを直せないのがつらい、という指摘から、入力欄を編集できる形にした。

- ← → でカーソル移動、Home / End で端、文字のクリックでその位置へ。Delete はカーソルの後ろの 1 文字
- 組み立て中なのはカーソルの直前の 1 音節だけ（ふつうの IME と同じ）。カーソルを動かすと確定する
- Backspace は確定した文字の上でも字母を 1 つずつ消す（애 の後ろで Backspace → ㅇ、ㅔ → 에）
- なぞりタイピングはカーソルを末尾に固定する（次のキーのガイドが末尾を前提にするため）
- 中身は `static/components/compose-buffer.js`（画面から切り離して Node でテスト）、描くのは `typing-field.js`

## ポータルと言語ごとの URL（2026-10-24）

suburi と同じく、ポータルから言語を選ぶ形にした（ユーザーの指摘。`/` がいきなり韓国語のホームになっていた）。

- `/` はポータル、`/settings` は設定、言語ごとの画面は `/{言語}`・`/{言語}/learn`・`/{言語}/words`
- 言語ごとの画面は同じ HTML を返し、画面の JS が URL の最初の部分から言語を読む（`<body data-scope="language">`）
  - HTML のリンクは `/ko/...` を書いておき（JS が動く前もたどれるように）、`data-lang-path`（と `data-lang-query`）を持つリンクを JS が今の言語の URL に書き換える
  - 画面側の言語パック（キー配列・組み立て）は `static/langs/<言語>/pack.js` が `registerLanguagePack` で登録する。言語を足したら learn.html にその言語のスクリプトを足す
- 設定は「全体」と「言語ごと」に分けた
  - 全体: 表示（テーマ）。ブラウザの localStorage
  - 言語ごと: 新出の数・反応時間の基準・面を出し始める日数・読み上げの速さ・キーボードの英字。`records/settings.json` の `{"languages": {"ko": {...}}}`。言語によって変えたくなるため
  - 設定の画面は 1 つで、言語を切り替えて開く（`/settings?language=ko`。言語の画面の「設定」から来たときはその言語）
- 言語を URL に入れる前の `/learn`・`/words` は、最初の言語の画面へ転送する（開いたままのタブのため）
- API は言語を必ず受け取る（既定の言語を持たない）。`GET /api/portal` でポータルのカード、`GET|PUT /api/settings/{言語}` で言語ごとの設定。API の版は 2

## 見た目の方針（2026-10-24）

画面の崩れとごちゃつきの指摘（何でもカードで囲む、値がバラバラ、薄紫の使いすぎ）から、見た目を作り直した。方針は「ハングルが主役で、キーボードで操作する集中モード」。

- 書体は Pretendard JP の 1 書体で韓国語・日本語・英字を揃える。ローカルで動かすので `static/fonts/` に同梱する（SIL OFL、`static/fonts/LICENSE.txt`）。Google Fonts は読まない
- 色はグレーの濃淡とアクセント 1 色。アクセントは進み具合・選択中・新出の単語にだけ使う。押すべきボタンは白黒反転（`--primary-*`）、緑と赤は正解・不正解の表示専用
  - いちばん薄い文字色 `--text-3` は背景とのコントラストが 3:1 ほどなので、飾り（区切り記号・アイコン・枠）と大きな文字だけに使う。読ませる文字（ヒント・品詞・見出しなど）は `--text-2`
- 値は段階から選ぶ: 余白 4/8/12/16/24/32/48、角丸 6/10/16 と丸、文字 12〜32px の 7 段階＋ハングル用の 36・48px（`static/style.css` の `:root`）
- 枠で囲むのは押せるもの（言語のカード、矢印ゲームの選択肢）と、ひとまとまりの面だけ。リストは区切り線にする
- 学習の画面は上部を「中断・ラウンドごとの進み・件数」だけにし、どの場面も「見出し → 主役と操作 → ヒント」の 3 段で、見出しとヒントの位置を固定する
- 矢印ゲームの選択肢は 4 つとも同じ大きさ（3 行で切る）。選んで正解は塗り、見逃した正解は枠だけ
- 画面のキーボードは実物と同じく段をずらす。答えが決まったら（正解、または 2 回目の答え）畳む。「直してみましょう」の打ち直しの間と、なぞりの間は出したまま（配列を見たい時期ほど打ち直しで見るため）
- 打つ場面は中身を上に揃える。結果が出てもキーボードを畳んでも、問題と入力欄の位置が動かないように（中央寄せだと採点のたびに 70〜80px 跳んでいた）
- 動きを減らす設定（`prefers-reduced-motion`）では、飾りの動きを止める。残り時間を見せる線は情報なので残す
- アイコンは線で描く SVG（`common.js` の `icon()`）。絵文字は OS で見た目が変わるので使わない
- ファビコンはユーザーが用意した画像（青地に白とミントの吹き出しの L）を縮小して `static/icons/` に置いた

## 本番の教材づくり（2026-10-24）

画面のたたき台ができたので、M2〜M6 より先に、L1 の本番の教材を一度作って流し込むことにした（ユーザーの判断）。
教材づくりは `tools/` の CLI（`uv run langlang-build`）で回す。手順は `docs/plan.md` の 6 章のとおりで、決めたことは次のとおり。

- 途中のデータは `content/ko/work/` に置き、Git で管理する。AI の結果は項目ごと（候補の見出し・帯・ユニットごと）に保存し、再実行したときは済んだところを飛ばす。プロンプトを直したら `app/prompts.py` の `*_STYLE` を上げると、その段階だけ作り直す
- 元のリスト（国立国語院「한국어 학습용 어휘 목록」の txt）は `content/ko/sources/nikl.txt` に置く（Git 管理外）
- 候補
  - 同じ見出しが品詞違いで複数行あるもの（오늘 の名詞と副詞など）は同じ語なので 1 語にまとめる。補助用言だけの見出し（싶다 など）は文法なので除く
  - 頻度順位が空の行（固有名詞と 구십 など）は、段階の中で最後に並べる
  - 固有名詞は除くが、国名・大陸名と 서울 は残す（自己紹介や日常会話で使うため）。判断は粗い付与の AI に任せる
  - 補完は、あいさつの決まった表現（안녕하세요 など。リストは辞書形の語だけなので）と、2003 年より後の日常語（스마트폰 など）を AI に挙げさせる。既存の語の活用形と同じ形の語（SNS の「좋아요」は 좋다 の 좋아요 と同じ）は、学習者が取り違えるので外す
  - ハン検の級は推定なので、推定が明らかにずれた語（同じ漢字の 인사＝あいさつ／人事 を見分けられないなど）も平均でならされる。公式の語彙リストが手に入ったら上書きする（計画どおり）
- 固定枠は 1 ユニット（20〜30 語）に収まらない（約 95 語）ので、L1 の最初の数ユニットにする。並びは AI が学ぶ順に決め、1 つ目はあいさつと自己紹介
- ユニット分け: スコアの順に約 200 語ずつの帯に分け、帯の中で AI に場面ごとにまとめさせる。帯の中のユニットは平均スコアの低い順。場面のまとまりと、難しさのなだらかさ（6.1 の「グラデーション」）を両立させるため
- 文法: L1 の文法リストを AI に作らせ、それぞれの文法を最初に使ってよいユニットを決めさせる。文はそのユニットまでの単語と文法だけで作る（最初のユニットから文を作れて、難しい文法ほど後に出る）
- 単語の検算で意味か漢字が食い違った語は、計画どおり「要確認」にして 2 つの案を `review` に残す。文を作るときは検算の案の意味を使う
- 単語の検算では語種も確かめさせ、食い違ったら検算の案に直す（要確認にしない）。語種は粗い付与で速いモデルが付けたもので、食い違いの多く（漢字語＋하다 を混種語とするか など）は検算の案のほうが一貫しているため
- 文の検算
  - 機械（Kiwi）: 語節と `word_ids` が文と合っているか、使ってよい単語だけか、そのユニットの単語が 1〜3 語か。`word_ids` の抜けは、同じ綴りの語が 1 つだけなら機械で足す
  - Kiwi の分け方と見出しが食い違うところは問題にしない: 一覧にない固有名詞（人名）、依存名詞（文法の一部になるもの）、使ってよい語に分けられる合成（스물다섯、역사책）、名詞＋하다 の 하 に付けた 하다
  - Kiwi は文の中で解析を 1 つに決め打ちするので、見つからない語は、語節だけの上位 5 つの解析と活用の規則（살다 → 사세요、계시다 → 계세요）でも探す。全ユニットを作ったとき、要確認 50 文のうち 28 文がこの種の誤検出だった
  - 落ちた文には、どちらの検算で落ちたかを残す。機械の検算を直したら `sentences --recheck` で、機械の検算で要確認になった文だけを確かめ直す
  - AI: 自然さ・訳・文体と文法の表示・穴埋めのヒント。許容例の誤りは文を落とさずに取り除く
  - 落ちた文は問題を添えて作り直させ、2 回落ちたら「要確認」。最後に、どの文にも出てこないユニットの単語の文を 1 回だけ足す
  - 文法の表示と許容例の誤りは、落とさずに検算の案で直す。単語の確認は、同じ綴りの別の語を指していないかだけにする（試した 2 ユニットで、同じ 아니에요 を逆の理由で落としたり、주다＝あげる／くれる のような訳し方の違いで正しい文を落としたりしたため）
- 文の生成は、計画の既定（opus・既定の effort）だと 1 回 4〜17 分かかり、利用枠も多く使う。今回は `LANGLANG_ENRICH_EFFORT=medium` で流した（1 回 1〜2 分）。質は別の呼び出しの検算で確かめる
- id: 単語の id はユニットに入れたときに学ぶ順に付け、`work/ids.json` に残して変えない。文の id はユニットの中の枠の番号で、作り直しても同じ枠なら変わらない
- 書き出し（`export`）で `content/ko/` の教材を作り直し、`work/report.md` に要確認の一覧などをまとめる。テストデータ（3 ユニット）は本番の教材で置き換えた

## 採点の段階（2026-11-04）

ほぼ正解の答え（書き取りの 누구애요、穴埋めの 미야내요）が、完全一致しないだけで不正解になっていた。ユーザーと決めたこと:

- 機械で決めるのは「正解」と「正解（注意つき）」だけ。空白の位置だけの違いに加えて、発音どおりの形に直すと一致する答え（綴りだけが違う）も注意つきにする。発音の形への直し方は言語パック（`app/langs/ko.py` の `pronounce`）に置き、よく出る規則だけを扱う
- 「9割合っていれば注意」は入れない。1字違いでも意味が変わる誤り（있어요／없어요、해요／했어요、는／를）があり、機械では打ち間違いと見分けられないため
- 「9割合っていれば AI に回す」もやめて、機械で決まらない答えは練習の種類を問わずすべて AI に判定させる（ユーザーの判断。取りこぼしを出さないため）。書き取り・穴埋め・綴りも含む
- AI の判定の粒度をそろえるため、プロンプトは「不正解 → 注意 → 正解」の順に条件を確かめる手順と、共通の判定の例で書く。不正解のときは理由を書かせる
- 正解（Good）と注意つき（Hard）で FSRS の評価を分ける（計画の 5.1 のまま。記録を入れるときに使う）
- AI の判定は答えと一緒に保存して使い回す。学習の記録（SQLite）を入れるまでは `records/graded/<言語>.json` に置き、記録を入れるときに `graded_answers` に移す。模範解答が変わった文と、採点のプロンプトの版（`GRADE_STYLE`）が変わったときは使わない
- 画面は、AI の採点を待つ間「AI が採点しています…」を出す（1 回 15 秒ほど）。AI の `corrected` は学習者の答えを最小限直したものなので、模範解答と違えば「直した答え」と「模範解答」の両方を見せ、差分は直した答えと比べる
- 穴埋めの許容例は、空欄の許容例（`cloze[].variants`）と、文の許容例のうち空欄の語節だけが違うものを使う

## 許容例の作り直し（2026-11-04）

採点で AI を呼ぶ回数を減らし、正しい別の言い方をその場で正解にするため、L1 の許容例を作り直した（ユーザーの判断）。

- 文は作り直さず、許容例だけを作る段階（`langlang-build variants`）を足した。文を作り直すと文の中身も変わり、数百回の呼び出しがかかるため。ユニットごとに「作る（opus・effort medium）→ 機械で除く → 検算（opus・medium）」の 2 回
- 日→韓の許容例は、助詞や主語の省略、縮約、語順、同じ意味の別の語・語尾、決まった表現の 합니다 形と 해요 形を集める。해요체 の文に 미안합니다 のような 합니다 形の決まり文句が入っていて、해요 形でも答えられる文があったため（L1-U01-007 など）
- 穴埋めにも空欄の許容例（`cloze[].variants`）を持たせる。文の許容例から空欄の語節だけを取り出すと、ほかの語節も違う言い方では取り出せないため
- 発音が同じだけの許容例は機械で除く。뭐에요 のような綴りの誤りを許容例にすると、採点で注意つきにならず正解になってしまうため
- 書き取りは許容例を使わず、読み上げた文とだけ比べる。許容例を増やすと、読み上げと違う言い方（미안합니다 の書き取りに 미안해요）が機械で正解になってしまうため
- 検算で除いた許容例と理由は `work/variants/<ユニット>.json` の `rejected` に残す

## 学習の記録（2026-11-04）

採点の 3 段階がそろったので、学習の記録を入れた。3 段階に分けて入れる（ユーザーと決めた）: 1. 土台と単語、2. 文、3. 苦手と取り違え。この節は 1 の分。

- 記録は `records/langlang.db`（SQLite）の 1 ファイル。サーバーを止めても残る。`records/` は Git 管理外なので、バックアップはこのファイルをコピーする
- 忘却曲線は `fsrs` パッケージ（6.x）。1 日 1 回の学習なので、日の中の学習ステップ（1 分後・10 分後）は使わない（`learning_steps=()`）。新しい単語は Again なら翌日、Good なら 2 日後に出る
- 日の区切りは朝 4 時（夜中の学習を前の日として数えるため）。期限は日単位で見て、明日の 21 時が期限のカードも明日の朝の学習に出す
- FSRS を動かすのは、その日のその面の最初の解答だけ。判定はサーバーがするので、画面は解答をすべて送る（最後尾に回ったあとの正解や、同じ日の 2 回目の学習は `counted = 0` で残る）
- 初見カードでは記録せず、そのあとの最初の出題でカードを作る（4.4）。1 日の新出の枠は、今日カードを作った単語の数で数える
- 面の出し始め（聞き取り・逆引き・綴り）も、この段階で入れた。カードは面を区別せずに扱えるので、分ける理由がなかった。ただし、もとの面を今日答えた単語は、次の面を明日から出す（初めての単語を「簡単」と答えると安定度が 8 日ほどになり、その日のうちに聞き取りと逆引きまで出てきて多すぎるため）
- 綴りの面の評価は採点の判定から決める（正解 Good、注意つき Hard、不正解 Again）
- 復習が上限（`review_limit`）を超えたら、思い出せる確率の低いものから出す
- ホームのユニットのリンクは「ユニットの練習」にした。そのユニットのまだ出していない単語を新出に、出した単語を意味の面で出す。記録はする（同じ日の 2 回目以降は FSRS を動かさない）
- 文はまだ記録を持たないので、まだ見ていない語が 1 語以下の文のうち、今日の新出の単語、次に復習の単語を多く含む文を選ぶ
- 解答の記録は待たずに次へ進む（矢印ゲームのテンポのため）。記録に失敗したら、1 度だけ消えない通知を出す

## 文の記録（2026-11-05）

学習の記録の 2（文）。文も単語の面と同じ `cards` に 1 行ずつ持ち（`kind = 'sentence'`）、段階（`stage`）の列を足した。

- 単語と同じく、導入では記録せず、導入のあとの最初の出題（段階 1）でカードを作る。1 日の新しい文の枠は、今日カードを作った文の数で数える
- 段階は FSRS と同じく、その日の最初の解答でだけ動かす（正解・簡単で 1 つ上、注意つきでそのまま、不正解で 1 つ下。1〜5）。打つ練習は 1 回目の判定で記録し、自分で直したあとの答えは使わない
- 段階の練習: 1 聞いて選ぶ、2 穴埋め、3〜5 書き取り。穴埋めのない文は書き取りにする
- 産出（日→韓・応用作文）は 1 日 3 問まで（`OUTPUT_ITEMS`）。期限が来た段階 3 以上の文から、思い出せる確率の低い順に回し、段階 4 は応用作文、3 と 5 は日→韓にする。産出に回らなかった段階 3〜5 の文は書き取りにする。段階どおりに全部を産出にすると、1 日に 7 文ずつ新しい文が入る分だけ作文が増え、計画の「産出 2〜3 問」に収まらないため。文法の表示がない文は、応用作文の代わりに日→韓
- 新しい文は導入のあと 2〜3 問はさんで出す。復習の文で間を埋め、それでも足りない列の終わりでは導入を前に出す（初日のように復習がない日は、最後の文が導入の直後に出ていたため）
- 文の復習の上限は、単語とは別に `review_limit` を使う
- ユニットの練習では、そのユニットの文のうち、記録のある文をすべて段階の練習で出し、まだの文を新しい文として出す
